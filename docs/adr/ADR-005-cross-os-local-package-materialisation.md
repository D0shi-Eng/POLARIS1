# ADR-005 — Cross-OS materialisation of the local `@polaris/contracts` dependency

**Status:** Accepted (2026-09-03). Supersedes the package-realisation half of the
W4 remediation recorded in `docs/phases/PHASE-00/W4-PACKAGE-RESOLUTION.md`.
Does not touch ADR-002; it is what makes ADR-002 hold on two operating systems.

## Context

`runtime` depends on the contracts package as a local directory:

```json
"@polaris/contracts": "file:../contracts"
```

`D:\POLARIS` is a single working tree reachable from **two** operating systems —
Windows natively, and Linux through the shared mount. Both run `npm` against the
same `node_modules`.

By default npm realises a `file:` dependency as a **link**. A link is not a
declaration; it is a filesystem object, authored by whichever npm ran last, in
the only form that npm's host understands:

| authored by | object | seen from the other side |
| --- | --- | --- |
| Linux npm | POSIX symlink | Windows cannot traverse it → `TS2307` |
| Windows npm | NTFS junction | Linux `existsSync` returns **false**, `readdir` returns `EIO` |

Both directions are recorded, natively, from the sides that observed them:
native run 3 (`evidence/w4-verify-runtime.log`, `TS2307` × 11) and
`evidence/w4-package-cross-os-link.local.json` (the Windows junction written at
08:52 on 2026-09-03, probed from Linux).

The previous decision was to **keep the link and repair it**: detect an
untraversable entry, delete the tree, `npm ci`, re-measure. That is correct as
far as it goes, and it did work — the gate passed 9/9 natively on Windows at
09:36 UTC. But it makes every alternation between the two operating systems a
full reinstall, it leaves retired `.contracts-*` entries behind when an install
is interrupted, and it means the *health* of the dependency depends on which
machine touched the directory last. Detection is not robustness.

## Decision

**Materialise the local dependency as a packed package, never as a link.**

`runtime/.npmrc` — repository-owned, so it applies to every install by every
person and every machine, not to one hand-typed command:

```
install-links=true
```

npm then packs `../contracts` (honouring its `files` field) and installs the
result into `runtime/node_modules/@polaris/contracts` as an ordinary package:
plain files, no reparse point, nothing for either operating system to traverse.
The materialisation form is named in the evidence as `PACKED_PACKAGE`.

The declaration is unchanged. `file:../contracts` stays in `runtime/package.json`;
only its *realisation* changes. `runtime/package-lock.json` was regenerated and
now records

```json
"node_modules/@polaris/contracts": { "version": "1.0.0", "resolved": "file:../contracts" }
```

with no `"link": true` and no `"../contracts"` entry.

### Consequences

- **Build order becomes mandatory, and enforced.** The pack takes whatever is on
  disk. Materialising `runtime` before `contracts` is built produces a package
  with no `dist/` — the install *succeeds* and resolves nothing. `contracts`
  installs and builds first; `runtime` materialises after. The gate names this
  failure `POLARIS_CONTRACTS_NOT_BUILT` at PKG-07 instead of letting it surface
  later as `TS2307`.
- **The contracts package's own dependencies enter the runtime tree.** `ajv`,
  `ajv-formats` and their transitive dependencies are now installed under
  `runtime/node_modules` as well. `ajv` stays pinned at `8.20.0` by contracts'
  exact specifier; `npm audit` reports **0 vulnerabilities** in both packages.
- **`runtime` must be re-materialised after a contracts rebuild.** The gate
  compares the installed export surface against `contracts/dist` by content
  hash and reports `POLARIS_PACKAGE_MATERIALIZATION_STALE`, which the runner
  treats as repairable.
- **Installing `runtime` now needs the registry** for those transitive packages,
  where a link resolved them through `contracts/node_modules`.
- **ADR-002 is unaffected.** The installed copy is a package-manager artefact:
  generated by `npm`, ignored by git, and proven byte-identical to the build. The
  duplication ADR-002 forbids is a second *source* under `runtime/src`, and
  PKG-10 still measures that by content hash.

### The cross-OS invariant

> No operating system may leave `runtime`'s package resolution in a state the
> other cannot use.

Resolution is now decided by ordinary files, so link authorship is irrelevant to
it. `node_modules` as a whole remains **host-owned** — `.bin` entries are `.cmd`
shims on Windows and symlinks elsewhere — so the runner stamps every tree it
installs with `node_modules/.polaris-host.json` and reinstalls when the stamp is
missing or names another platform. Ownership is measured, not inferred from a
link that failed to open.

## Alternatives considered

- **Keep the link, keep repairing it.** Disproven as *sufficient*: it makes every
  cross-OS alternation a reinstall and leaves the tree's validity dependent on
  which machine ran last. Retained only as the fallback the runner still performs
  when the gate reports a repairable code.
- **`npm pack` into a tarball committed or built into `runtime`.** Equivalent
  outcome, more machinery: a build step, an artefact path, and a staleness
  question that `install-links` answers inside `npm ci` itself. Kept as the
  documented fallback if `install-links` ever proves insufficient.
- **A root npm workspace.** Merges two independently audited lockfiles and
  re-resolves the whole graph across the AJV remediation — and links through the
  *same* symlink mechanism, so it would not have prevented this at all.
- **Turborepo / Nx / pnpm / Yarn.** Not needed to link one local package.
- **`NODE_PATH`, `npm link`, a `tsconfig` path alias, copying the source.**
  Rejected. The first three make one resolver agree while the others disagree —
  a `tsconfig` alias satisfies `tsc` and leaves the package broken at run time.
  The fourth violates ADR-002 outright. PKG-11 fails the run if `NODE_PATH` is
  set at all.
